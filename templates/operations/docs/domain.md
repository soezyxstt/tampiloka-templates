# Operations domain and API (integration contract)

UI imports `src/domain/contract.ts`. All endpoints are same-origin, no-store. A successful command returns `{result,state}`; failures use `{error:{code,message,details}}` and non-2xx status. Do not show success before receiving a result. Keep command UUID across retries; use GET `/api/commands/:id` after lost responses. Payload mismatch returns 409.

- GET `/api/session`: `{user,csrfToken,demo}`; unauthenticated user is null.
- POST `/api/demo/session` `{persona}`: demo only; persona IDs `owner`, `inventory`, `receiver`, `cashier`, `pricing`, `auditor`, `mixed`. Creates isolated demo installation on first login; switching personas keeps its data. Response matches session.
- POST `/api/login` `{username,password}`: real installation credentials provisioned as Worker secrets (see deployment section).
- GET `/api/state`: filtered `StateSnapshot`, including balances and actionable exceptions. Poll every 3 seconds while visible; display age/errors.
- POST `/api/commands` `{id,type,payload}` with `X-CSRF-Token`: atomic result and current filtered state.
- POST `/api/logout` with CSRF.
- GET `/api/report?locationId=&city=&productId=&from=&to=&basis=recorded|occurred&format=json|csv`: same scoped data, totals and explicit basis.
- GET `/api/backup`: owner-only versioned snapshot plus commands; POST `/api/restore` with CSRF and backup restores only an empty matching real installation. Existing history cannot be overwritten.

Common payloads: `locationId`, `productId`, `quantity`, `unit`, `condition` (`sellable|held`), `reason`, `occurredAt`, `sourceId`. Money integer IDR. IDs returned as `result.documentId`; use these for transferId/countId/shiftId/saleId/paymentId. For quote use `result.data.quote`; pass its `fingerprint` as `quoteFingerprint` when completing sale. Errors are stable machine codes with English messages suitable for translation.

Transfer: draft `{fromId,toId,lines:[{productId,quantity,unit?,condition?}],sourceId?}`; send/arrive/close/cancel `{transferId}`; receive `{transferId,lines:[{productId,quantity,condition?}],reason?}` in **base units**; supplement/loss/return `{transferId,productId,quantity,reason}`. Finding adds evidence without stock impact `{transferId,reason,evidence,responsibleId}`. Return here means confirmed goods back at origin; already received goods require a new reverse transfer.

Stock: open/receive `{locationId,lines,source,proof,reason,occurredAt?}`; adjust `{locationId,productId,quantity,condition,reason}` quantity signed; release/dispose `{locationId,productId,quantity,reason}` positive; reverse `{mutationId,reason}`. Count start `{locationId,productId,condition?}` captures server cutoff; record `{countId,physical}` unfreezes movement; close `{countId,reason}` applies delta; late-receive `{countId,transferId,lines,reason}` atomically compensates an old count adjustment and receives the matching units.

POS: quote/complete `{locationId,lines,customerId?,voucherCode?,shiftId?,quoteFingerprint?,paymentId?,payment?:{method,amount,reference?}}`. Quotes use current server prices. Complete requires open own shift; payment can be recorded separately with `{locationId,shiftId,method,amount,status,reference}`. Payment review/pending never finalizes sale. Zero bill has `not_required`. A separate payment remains visible if a later sale fails. Return request records a pending approval; owner finalizes sale.return `{saleId,lines:[{lineIndex,quantity,condition}],reason,shiftId?}`; refund without goods `{paymentId,amount,reason,shiftId?}`. Refund never silently returns voucher quota. shift open `{locationId,openingCash}`, cash `{shiftId,amount,reason}`, close `{shiftId,countedCash}`, correction `{shiftId,amount,reason}` retains original closed report.

Masters: owner sends full `location` / `product` / `user` objects to matching commands; business `{name,timezone,modules}`. Pricing sends full `price`, `promotion`, `profile` objects. `locationId:'*'` is explicitly business-wide and requires business-wide pricing scope. Imports `{importId,rows:[{kind:'product'|'location'|'opening',...}]}` preview returns row errors; apply is all-or-nothing and opening import IDs cannot repeat.

No build, typecheck, install, browser or heavy suite has been run: explicitly prohibited for this task. Lightweight single-process Node checks are recorded below. Runtime/performance, disaster recovery and acceptance results remain unverified.

## Coordination additions

Demo login also accepts `{mode:'inventory'|'retail'|'full',preset:'food'|'retail'|'supplies',newSession?:boolean}`. The server changes enabled modules within the selected preset; every preset has its own durable dataset, preserving its business state and money snapshots when switching away and back. Initial sample balances and prices come solely from validated `config/operations.json`. Existing demo sessions are required to switch personas. `newSession:true` creates a new isolated dataset (also use it after session expiry). Theme remains UI-only. Production ignores demo parameters.

`transfer.resolve` requires owner `{transferId,findingId,reason}`. Each finding remains independently open even if all transit is received. `payment.resolve` requires owner `{paymentId,status:'confirmed'|'failed',reason}`; pending/review payments block shift close. `sale.return` accepts `refund:false` to receive goods without paying money again after a prior money-only refund. For direct owner approvals, `reason` records the explicit approval rationale; when `selfApproval:true`, `exceptionReason` is mandatory.

## Deployment and real authentication

Worker exports `OperationsStore`, bound as `OPERATIONS`, with SQLite `new_sqlite_classes` migration v1 (already in scaffold Wrangler configs). `worker/platform.d.ts` describes the minimal runtime API because this scaffold has no generated Cloudflare types; generate/verify official binding types before release. SQL schema is also documented under `migrations/0001_operations.sql`; do not apply it as D1.

Set `OPERATIONS_AUTH` as a secret JSON array of `{username,userId,salt,hash,iterations,kdf,passes}`. Salt and hash are hexadecimal (at least 16 random salt bytes and 32 hash bytes). Use `kdf:"pbkdf2-sha256-chain-v1"`, `iterations:100000`, and `passes:3` (3–10 allowed). Starting with the exact UTF-8 password bytes, run PBKDF2-SHA256 with the salt and 100000 iterations, 256-bit output, then use the raw output bytes as the password for each following pass with the same salt. Store the final output as hexadecimal. This is a versioned chained format, **not** standard PBKDF2 at 300000 iterations. Earlier documented unversioned 210000-iteration credentials must be reprovisioned; they are rejected explicitly rather than silently reinterpreted. This avoids the per-call workerd PBKDF2 limit ([upstream implementation](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/crypto/pbkdf2.c%2B%2B)). Native hashing runtime still needs verification on the deployment compatibility date. Initial real user ID is `owner`; use access.save to create additional accounts before provisioning their credentials. No default production password exists. Credentials are compared through Web Crypto HMAC verification. Sessions store SHA256 hashes of opaque random tokens, expire after 12 hours, and use HttpOnly/SameSite=Strict cookies (Secure + __Host prefix on HTTPS). The worker never accepts a client business ID for routing real data. Set `BACKUP_SECRET` to a random secret of at least 32 characters. Keep backup envelopes securely outside the application and test restoration in a matching, empty installation. Restore requires owner authentication within the last 15 minutes, verifies the same business and preset, and invalidates all sessions.

Atomicity uses synchronous SQL transactionSync around fresh read, authorization, reduction, immutable evidence inserts, state projection, and idempotency result. There is no external I/O inside this transaction. State is copy-on-write and never cached before commit. Ledger tables only insert; master and workflow projections can change, with original payloads in append-only documents/journal. A failed command rolls back every SQL write.

Current scaling limitation: projection is one JSON row and reducer/report traverses history; this is suitable for functional pilot validation, **not yet proven for the 200000-mutation target**. SQL evidence tables are separate and append-only, but paged/indexed projections and retention policies need implementation before that load claim. Opt-in scheduled R2 backup and bounded retention are implemented but not deployed or runtime-verified. No restore drill, RPO/RTO measurement, monthly availability evidence, automatic payment provider, file-upload scanning/storage, or offline finalization is claimed. Proof fields accept references only; they are not an upload service.

Further API notes: GET `/api/commands/:id` returns `{result,state}` (same envelope as POST), after checking current permissions for the original action. GET `/api/search?q=...` searches only visible documents, returning up to 100 matching records and a total; GET `/api/documents/:id` enforces the same filter. `stock.propose` / `master.propose` accept scoped `locationId` and `reason` from inventory/receiver; owner approval commands reference the proposal via `sourceId`. They never mutate stock themselves. External source/evidence pairs cannot be silently entered again. An owner approving a document they originally created must additionally provide `exceptionReason` (or when `selfApproval:true`). UI forms need that field for self approval.

A count freezes ordinary movement while physically counting. An already-arrived shipment may still be booked to resolve the pending-arrival blocker; `count.record` then captures a refreshed cutoff and baseline. Arrival must be booked before recording the physical quantity. Late count correction requires an explicit `occurredAt` at or before the count cutoff. Findings remain exceptions even with zero transit. Goods shipped as held remain held on receipt until owner release. Zero-total POS accepts omitted payment or a zero-amount UI payment object, and always stores `not_required` without inventing received money.

## Preset isolation and destination directory (final integration)

`StateSnapshot.transferDestinations` is a minimal active-location directory (`id,name,city,kind,active`) available only to owner/inventory users. Use it exclusively for the transfer draft **toId** picker. `locations`, balances, reports and exports retain their existing permission scopes. Receivers and cashiers do not gain a business location directory.

Demo `POST /api/demo/session {persona,preset,mode}` now routes to a separate Durable Object named `demo:<random-installation-root>:<preset>`. The cookie retains the selected preset. Switching between presets checks the currently authenticated source session and CSRF before allowing login into the destination dataset. Returning to a previously opened preset loads its prior stock, documents, prices, users and shifts; it does not rename or reseed its products. The root persists while switching. `newSession:true` creates a fresh root and all-new isolated datasets. Production stays at `real:<configured-business-id>` and never uses these demo stocks or preset overrides.

Food uses configured Cimol products/units and business. Retail seeds Ruang Ritel Contoh with KAOS-KATUN-M (pcs/lusin) and TAS-KANVAS (pcs/pak), prices 125000/65000. Supplies seeds Bekal Kantor Contoh with KERTAS-A4-80 (rim/karton) and PENA-HITAM-05 (buah/kotak), prices 55000/8000. Each nonfood preset has a distinct business ID, product IDs, SKU, units, conversion factors and identity; initial quantities are remapped from validated demo opening config. Mode remains independent and only enables new capabilities in that preset. Theme remains visual. This routing/return flow has not been run in a Workers/browser runtime during this task.

Ownership handoff: parent now owns `src/domain/report.ts` for report/filter/CSV refinements; this domain task stopped editing it at handoff. The additional preset/directory and payment-history tests were written and syntax-checked only, and still require execution after integration. Initial product imports reject IDs/SKUs that already exist; use the audited master command to update an existing product.


## Adversarial hardening, 10 November 2026 (supersedes earlier unexecuted-test notes)

This pass changed only Worker/domain-owned files and `tests/hardening.test.mjs`. It ran no install, build, typecheck, browser, Workers runtime, load dataset, or subagent. All listed Node checks use one process and a 64 MiB heap cap; they are functional regressions, not full AT01–40 certification.

Changes:

- Login attempt reservations commit before password hashing; the eleventh attempt in a fixed 15-minute IP window is rejected before PBKDF2. Unexpected-error logs contain only a fixed event/category, never exception messages or secrets. API browser requests with a cross-site `Sec-Fetch-Site` are rejected, and each read/replay resolves the active account and current roles.
- Unit lookups use own properties; nested prototype keys are rejected in command data and restored state. Journals use own-property reads/null-prototype maps. `__proto__` as a command identity cannot poison storage.
- Explicit source references require visible evidence. Proposal approvals match kind/location and cannot resolve twice; master proposals require inventory rights, while stock proposals allow inventory/receiver. External source/proof matching trims whitespace and checks imported evidence. Known internal location sources must use transfers.
- Restore checks duplicate identities, role scopes, mutation/document actors and containers, correction links, shipment balances, payment/sale links, all sale component sums and stock quantities, refund limits, and frozen shift arithmetic. Journal fingerprints, actors, results and payloads match evidence before any write. New documents retain `input` separately so derived output (notably import row counts) cannot overwrite original command evidence. Invalid restores roll back; successful restores revoke sessions. Old import backups that lack the newly retained input may fail strict journal validation and need an explicit reviewed migration; do not bypass validation.
- Refunded unallocated payments cannot fund another sale or be reclassified as never received. A failed inline sale with asserted positive collected money preserves a separate `review` payment on the common price/stock/voucher/short-payment failures, returns `error.details.paymentId`, and blocks duplicate collection under that command identity. That payment blocks shift close until reviewed/refunded. Its separate recovery journal uses the reserved `collected-` prefix; client commands cannot claim that prefix. Recover the payment, resolve it, and complete a new explicitly confirmed command with `paymentId`, or refund it. A successful command lookup still returns `{result,state}`.
- Disabling POS blocks new carts, prices, quotes, sales, payments and normal shifts; disabling commercial blocks new promotions/profiles. Replays and settlement of historical evidence remain available. `shift.open {locationId,openingCash,settlement:true}` can open a cash settlement shift for existing payments even with POS disabled. Commercial requires POS. Commercial profiles accept optional `startsAt`/`endsAt`; equal-priority overlaps are rejected and the end instant is exclusive. Original quote snapshots remain unchanged.
- Two-part legacy demo cookies keep routing the original food dataset (`demo:<root>`), including its journal. A `.legacy` marker survives switches to other presets and back. New sessions use preset-specific objects. Switching back restores the prior dataset; neither state nor journal is copied between presets.

Targeted regressions cover prototype identities, reference scope and duplicate approvals, refunded-payment reuse, separate goods/money returns, component rounding against immutable original quotes, module settlement, scheduled profiles, corrupted restore/journal rejection, actual SQLite rollback and restore, frozen shifts, pre-hash throttling, bounded KDF passes using a mock (no expensive hash), and an actual Worker-handler preset round trip using small SQLite adapters. These adapters do not emulate the Cloudflare runtime.

Remaining substantial boundaries: whole-state/history scans need indexed/paged projections before the specified load target; scheduled off-site backups and bounded retention are implemented as opt-in features, but no deployed schedule, measured restore drill or monthly availability evidence exists. Evidence fields remain references, not uploaded/scanned files. UI recovery must consume `error.details.paymentId` and the changed credential provisioning format; those integration files belong to the parent. Historical transfer/count workflow projections are not a full reconstruction at an old report cutoff. Load, browser, deployment-native crypto and full acceptance remain unverified. This pass does not claim production readiness.
